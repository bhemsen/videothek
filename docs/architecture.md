## Boundaries

- Only `src/config.js` reads `process.env` (sole exception: the converter double `test/helpers/converter-stub.js`, which stands in for the external converter process and only reports the environment it received).
- Only `src/media/paths.js` turns client-supplied identifiers, DB-stored relative paths (`rel_path`, `output_rel`) or converter-reported paths into filesystem paths; everything else receives validated absolute paths. Paths the conversion code composes itself from the hex `storage_key` and fixed names (`.videothek-work/`, `out/`, `web.mp4`, …) under `CONVERT_DIR` are internal and need no guard.
- Only `src/convert/run-converter.js` starts a child process (the configured converter, argv without shell, allowlisted env); only the conversion queue (`src/convert/queue.js` and its helpers `job.js`/`publish.js`/`work-dir.js`/`sidecars.js`/`cleanup.js`) deletes or replaces files, and only under `CONVERT_DIR` (the per-job work area `.videothek-work/`, the publish `rename` that replaces a stale copy and its old `sub-*.vtt`, and the cleanup pass, which removes only 64-hex directories, never through a symlink). On POSIX every signal the queue sends goes to the converter's process group.
- Converter contract (the converter's side; the app hands it over through argv, `cwd` and the temp env and checks it with the stub converter in tests, but cannot enforce it on a child process): the converter only reads its source and creates or changes files only inside the per-job output and temp directories it is given. OS permissions (a service user with read-only access to `MEDIA_ROOT`, README) are the only enforcement that also covers the child. Record shapes, interpretation rules and exit codes: `docs/specs/spec-converter-adapter.md` (Converter contract; minimum `bhemsen/converter` v3.2.0, sidecars from v3.3.0).
- API clients reference media by index id, never by raw path.
- `src/library/` knows nothing about HTTP or users; `src/api/` knows nothing about file formats.
- `src/db/` is the only place with SQL.
- `public/` talks to the server exclusively via `/api/*` JSON, the JSON auth endpoints `POST /login` / `POST /logout`, page routes and media stream URLs.
- Data split: `MEDIA_ROOT` (read-only source) vs `DATA_DIR` (SQLite file: users, sessions, progress, derived library index, conversion state) vs `CONVERT_DIR` (default `DATA_DIR/converted/`: verified copies in `<sha256(rel_path)>/`, per-job staging in `.videothek-work/`; derivable but expensive).
- `library_items.playable` means "streamable via `/media/:id`": the source plays directly, or a fresh conversion exists (`status = 'playable'` with the item's current size/mtime). The flag is computed in `upsertItem`'s SQL and set in the conversion publish transaction, so every reader stays conversion-agnostic. Known exception: when the copy file of a fresh row is removed outside videothek (by hand, or `CONVERT_DIR` changed without moving the copies), the flag stays 1 while `/media/:id` answers `404 not_found` until the next cleanup pass deletes that row and resets the item's flag (`playable = 0, scan_version = 0`, so the next scan recomputes it; `docs/specs/spec-converter-adapter.md`; README: "CONVERT_DIR nur zusammen mit den Kopien verschieben"). Without a configured converter no cleanup runs. When not a single referenced copy exists (e.g. `CONVERT_DIR` moved without its copies, or its disk unmounted), the unmounted-disk guard skips this reconciliation and logs `conversion_cleanup_skipped`; the admin restores the copies or re-points `CONVERT_DIR` (README).
- Progress is keyed by `(user_id, rel_path)` and never references `library_items` by id.

## Key flows

1. **Scan:** startup (deferred so `listen()` never waits), a debounced watcher event or the periodic rescan timer -> `scanner` walks `MEDIA_ROOT` -> category parser classifies each file (category, grouping, title, playable flag) -> index rows upserted by relative path (`library_items`; `library_series` grouping rows for the `series` category), vanished rows deleted — except under a category root (or `MEDIA_ROOT` itself) that still has rows but is currently missing, unreadable or empty, which is protected instead (root safety: nothing under it is deleted, `lastError` reports why). Consequence for operators: emptying or removing a category folder never empties that category — to empty one on purpose, leave a single media file in it, or stop the service and delete the DB file under `DATA_DIR` (which also deletes every account, session and all playback progress, and all conversion state, so the copies under `CONVERT_DIR` are orphaned: no longer served, deletable by hand; the admin is then re-created from `ADMIN_USER`/`ADMIN_PASSWORD` — README "Medienordner"). Every completed run notifies `onScanComplete` listeners (Phases 5/6's extension point; Phase 8 registers the conversion queue's `requestCleanup()` there). Progress rows referencing vanished items are kept (item may reappear).
2. **Browse:** browser `GET /api/library/:category` -> session check -> DB query -> JSON list/grouping -> rendered by `public/` module.
3. **Stream:** `<video src="/media/:id">` -> `requireUser` -> id -> `library_items` row (`playable` check) -> path guard (a fresh conversion's copy under `CONVERT_DIR`, else the source under `MEDIA_ROOT`) -> `stream.js` answers `Range` with 200/206/416 chunks and closes the file handle after a 60 s idle timeout with no chunk sent; `HEAD` returns the same headers with no body, letting the player disambiguate a missing file (`404`) from an unsupported codec (`2xx`). `GET /media/:id/subtitles/:n` serves the `n`-th `.vtt` sidecar discovered by `src/media/subtitles.js` the same way.
4. **Progress:** identity is `(user, rel_path)`, never the index id -> `PUT /api/progress/:id` resolves the id to `rel_path` server-side, then upserts a keepalive report sent every ~10 s while playing and immediately on pause/ended/tab-hidden/`pagehide`. Opening an item fetches its position and seeks (auto-resume). The start page mounts the "Weiterschauen" row from `GET /api/progress?view=continue`, which merges the user's `in_progress` rows with next-up ("Nächste Folge") entries computed from series whose latest episode is finished. Music tracks and audiobook files report through this same path (`trackPlayback` / `PUT /api/progress/:id`) exactly like video, just with an audio finished rule (remaining ≤ 30 s, `src/api/progress-rules.js` `AUDIO_END_WINDOW_S`) instead of a next-episode lookup.
5. **Login:** `POST /login` -> scrypt verify -> session row + `HttpOnly; SameSite=Lax` cookie (`Secure` when behind HTTPS proxy). First start with empty users table creates the admin from `ADMIN_USER`/`ADMIN_PASSWORD`. JSON login, hashed session id, 30-day sliding expiry.
6. **Image metadata:** scan completes -> `onScanComplete` -> stub rows inserted for new `images` items -> sequential EXIF header reads (one file at a time) -> `image_meta` updated (capture date, orientation, thumbnail offset/length).
7. **Audio metadata:** scan completes -> `onScanComplete` -> `createAudioMetaPass` selects every `music`/`audiobooks` item whose `audio_meta` row is missing or stale (version, size or mtime changed) -> the category's folder-convention parser resolves grouping/title/disc fields -> `readAudioTags` reads ID3v2/FLAC tags (mp3/flac only; every other extension yields a path-only row) -> tags win over the folder for title/track, the folder wins for grouping and the disc-number fallback -> `audio_meta` upserted. Audio views only join in items that already have a row, so a new file appears once the pass has run (same ≤ 10 s freshness budget as video).
8. **Start page:** `/` mounts three rows into fixed slots in parallel: "Weiterschauen" (`GET /api/progress?view=continue`), "Weiterhören" (`GET /api/home/listening`; a music card links to `/music`, an audiobook card to `/audiobooks?book=<id>`, where the existing resume buttons start playback) and the category previews (`GET /api/home/previews`; empty categories hidden, "Alle anzeigen" links to the category page). A failed or empty request leaves its slot empty; "Willkommen" stays hidden while the requests load and shows only once all three have settled with every slot empty.
9. **Convert:** admin presses "Konvertieren" -> `POST /api/conversions/:id` (`requireAdmin`) -> `conversions` row `queued` (keyed by `rel_path`, `storage_key = sha256(rel_path)`) -> the queue claims one job at a time (FIFO) -> path guard resolves the source, and its size/mtime are recorded -> `run-converter.js` spawns `CONVERTER_CMD --to web|flac|opus --json <src> <CONVERT_DIR/.videothek-work/<key>-<unique>/out/>` (POSIX: own process group; nice 19) -> exit code + exactly one `file` record and a final `summary` record interpreted -> output checked by videothek's own sniff (`mp4-codec.js`/`compat.js`, FLAC/Opus magic), each reported WebVTT sidecar checked (inside `out/`, `WEBVTT` signature, size cap) and the source re-stat'ed -> sidecars renamed to `CONVERT_DIR/<key>/sub-<n>.vtt`, then atomic rename of the copy to `CONVERT_DIR/<key>/<fixed name>` -> one transaction sets the row `playable` (with its `sidecars` list) and `library_items.playable = 1` -> the item streams under the same id, its converted subtitles are listed after the source-folder ones, and progress is untouched. Any failure -> `failed` with a code, kept until an admin retries (no automatic retry). An admin cancel ends a `queued` row at once and a running one via `SIGTERM` (then `SIGKILL`) to the converter's group -> `failed` `cancelled`. After every completed scan (`onScanComplete`), the queue runs the cleanup pass between jobs. Every startup (feature on or off) and a graceful stop (after the stop deadline: at the next startup) turn a `converting` row into `failed` `interrupted`; `queued` rows survive. A source whose size/mtime changes makes its copy stale (not served; can be converted again).

## Where new code goes

- New media category -> parser in `src/library/parsers/`, register in scanner, list page in `public/`.
- New file format -> compatibility table in `src/library/parsers/compat.js` (+ tag reader in `src/library/tags/` if metadata needed).
- New endpoint -> `register<X>Routes(router, deps)` in `src/api/<x>.js`, one line in `src/http/routes.js`, test in `test/api/`.
- Schema change -> new numbered migration in `src/db/migrations/`; never edit an applied migration.
- New UI page -> `public/<page>.html` + `public/js/<page>.js`; shared UI helpers in `public/js/lib/`.
- Declared deviation — audio section: `public/music.html` and `public/audiobooks.html` share one module tree `public/js/audio/` (entry `app.js`) and `public/css/audio.css`/`audio-music.css`/`audio-books.css`, instead of a per-page `public/js/<page>.js`/`public/css/<page>.css`, because one persistent player must survive client-side `pushState` navigation between the two pages; its bottom bar drives a hidden `<audio>` with its own controls instead of the native `<video>`/`<audio>` controls design.md otherwise specifies, since native controls offer no previous/next, 15/30 s skip or queue title/cover (`docs/specs/spec-music-audiobooks.md` "Frontend file layout" and "Custom control bar" decisions).
- New config value -> `src/config.js` (the only `process.env` reader among `src/` modules; pure parsers may live in a sibling leaf module such as `src/config-converter.js`, called from `src/config.js`) + `.env.example` + README.
